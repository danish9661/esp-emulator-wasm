# PROTOCOLS.md — Peripheral Protocol Coverage Matrix (C3 / C6 / H2 / P4)

This document explains how peripheral protocols are emulated, lists every protocol
exposed by the ESP32-family virtual hardware, and tracks exactly which ones are
implemented, verified, or missing — per chip.

---

## 1. How Protocols Are Emulated

All protocols are bridged from the RISC-V firmware to the JavaScript host in two layers:

### Layer 1 — Assembly shims (in-flash patching)

At load time (`elf.mjs` → `planHooks` → `prepareSpiShims`), driver symbols in the
firmware's ELF are detected and their first instructions are overwritten with tiny
RV32I trampolines (see `shims.mjs`, generated by `spike/gen_spi_shims.py`). A shim:

1. Writes an **APC escape frame** into the virtual UART0 TX FIFO:
   `\x1b_ <kind> <payload> \x1b\\`
2. **Polls the UART0 RX FIFO status register** (`0x60000000 + 0x1C`) until the host
   pushes the reply bytes back via `uart_input`.

Because the shims use only base RV32I instructions, the *same bytecode* runs on all
four chips (RV32IMC / IMAC / IMAFC).

### Layer 2 — Host-side controllers (JavaScript)

`core/esp32c3.mjs` creates one controller per protocol; `core/uart.mjs` parses the
escape frames and dispatches to them, or to registered virtual devices
(`mcu.spi.register('sd', new VirtualSDCard())`, `mcu.i2c.register(0x3c, oled)`, ...).
Virtual devices live in `peripherals.mjs` and can be interactive in the web UI
(`worker.js`).

### Frame kinds

| Kind | Protocol | Direction | Payload |
|---|---|---|---|
| `W` / `R` | I2C | write / read | addr + data (nibbles a-p) |
| `S` | SPI | duplex | chunked byte streams, len-prefixed |
| `N` | NeoPixel (RMT) | write | pin + GRB bytes |
| `A` / `V` | ADC | read | raw / millivolts |
| `P` | PWM / LEDC | write | pin + duty |
| `I` | I2S | write | PCM bytes |
| `C` | TWAI / CAN | tx/rx | id, dlc, data |

Protocols that only touch CPU-visible MMIO registers (GPIO, UART0 console) need no
shims — the emulator's silicon model handles them natively.

## 4. Status Notes

### Implemented & verified (✅)

- All 10 Arduino sketches (`spike/sketches/`) run on all 4 chips with zero firmware
  changes — only driver symbol shims at load time.
- Verify suites: `spike/18-verify-all.mjs` (C3, 15 tests) and
  `spike/21/22/23-verify-*.mjs` (C6/H2/P4, 10 demos each) — all green.
- Virtual devices (interactive in the web UI): SSD1306, ST7789, NeoPixel strip,
  VirtualSDCard (FAT16/32), MPU6050, ADC/PWM/I2S/TWAI controllers.

### Emulator-supported but not wired (⚠️) — next candidate

- **Wi-Fi (C3/C6)**: the esp-emulator core already models 802.11 (soft-AP with SSID
  `myssid` / WPA2-PSK, station connect, IP assignment, TX/RX frames —
  `set_wifi_config` / `wifi_rx_push` / `wifi_tx_drain` in `pkg/esp_emu.js`). No shims,
  sketches, or tests exist yet for the ESP-IDF/Arduino Wi-Fi API. This is the largest
  untapped subsystem.

### Not supported (❌)

- BLE, 802.15.4, touch, USB, SDMMC, camera, DSI/parallel LCD, DAC: the emulator core
  does not expose these (no corresponding wasm exports), so they cannot be emulated
  without upstream work in esp-emulator itself.
- Note: BLE may partially exist in the emulator core for provisioning flows
  (see `pkg/README.md` chip-tool `ble-wifi` pairing) but is not exposed through the
  SDK API and has no verification.

### Native, untested (🟡)

- Timers, watchdogs, RTC, and flash-backed filesystems execute directly on the
  emulated silicon (no bridge required). They are used implicitly by the firmware
  during boot, but no dedicated regression test exercises them.

## 5. How to Run the Verification

```bash
node spike/18-verify-all.mjs      # C3 — 15 firmware tests (all protocols)
node spike/20-test-mcu-core.mjs   # modular SDK unit tests (I2C/SPI/ADC/PWM/TWAI)
node spike/21-verify-c6.mjs       # C6 — 10 demos
node spike/22-verify-h2.mjs       # H2 — 10 demos
node spike/23-verify-p4.mjs       # P4 — 10 demos
```

All suites must run with `mcu.step(100000)` (see AGENT.md — the WASM engine can drop
UART bytes at batch boundaries on H2/P4 with smaller batches).
